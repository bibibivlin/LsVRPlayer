# 项目维护

## 日常维护

- Issue 分别使用问题报告、功能建议模板；安全问题按 [安全政策](../SECURITY.md) 处理。
- PR 说明行为变化与验证结果；遵循 [贡献指南](../CONTRIBUTING.md)，依赖更新核对两处 Gradle 声明与许可。
- 在 [更新日志](../CHANGELOG.md) 的“未发布”部分记录面向用户的变化，不复制每轮测试和构建过程。
- 首页保持功能、截图、安装与文档入口简洁，详细实现和验证范围保留在 `Docs/`。

## 版本发布

沿用 [正式发布流程](Release.zh-CN.md)，保持版本号、Version Code、标签、版本说明和实际 APK 一致。当前发布徽章使用静态版本号，每次发布时同步更新 README。

整理“未发布”条目到新版本，记录兼容性变化；核对 APK 签名、SHA-256、发布清单和该包对应的测试范围。签名与测试成功不等于第三方分发条件已满足，APK 公开分发前另需完成 [许可核对](Licensing.zh-CN.md)。

## GitHub 设置

以下属于仓库服务端设置，提交文档不会自动启用：

- About 中设置准确的简介与主题，如 `vr`、`video-player`、`pico`、`unity`、`smb`、`emby`。
- 为默认分支配置适用的保护规则：通过 PR 合并，要求 `Release tooling checks` 中的 `checks` 检查通过，限制强推与删除。单维护者项目按实际情况设置审核人数。
- 保护发布标签，限制签名工作流、发布环境与自托管 Runner 的执行权限；不运行来自不可信 PR 的签名任务。
- 核对依赖告警、Secret scanning 与推送保护的可用性及配置，不将未启用的功能视为已有保护。
- 仓库公开前启用可用的私密漏洞报告入口，核对 [安全政策](../SECURITY.md) 中的联系流程。

仓库可见性由维护者明确决定。本次整理不改变可见性、分支规则或发布设置；当前私有仓库中的源码和 Release 仍只对授权用户开放。

## 公开前检查

确认 [许可证范围](Licensing.zh-CN.md)、第三方二进制分发材料、Git / Git LFS 历史及 Release 附件均适合公开。检查不能只看当前工作区，也要覆盖历史记录；发现泄露凭据时先撤销 / 轮换，再处理记录。不要将设备备份、真实账户、媒体路径、原始截图或签名密钥纳入公开材料。
