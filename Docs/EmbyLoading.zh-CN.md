# Emby 内容加载与 UI 响应修复

验证日期：2026-10-17。Unity 6000.3.23f1，Windows Editor、PICO A8110。

## 修改

原先网络等待已经异步，但收到响应后的 UTF-8 解码、JSON 反序列化、元数据归一化，以及完整媒体列表的去重和排序仍由 Unity 主线程执行。大响应和多页媒体库会占用处理 UI 输入与渲染的线程。

`EmbyClient` 现在在后台任务中解码、解析响应，并合并、去重、排序完整媒体库、演员作品和分类列表。下载结束后传递托管字节数组的有效区间，避免在主线程额外复制整个响应。首页、详情、分段、附加篇和播放资料共用同一响应处理入口。

UnityWebRequest 创建、状态检查、取消和释放保留在 Unity 上下文；页面发布仍在主线程。后台任务在处理前后检查取消，列表合并也逐项检查取消。旧页面请求取消后不能发布其结果。完整列表、重复页/截断页错误、排序、认证请求头、响应大小上限和禁止重定向的行为保持原有约定。

使用普通可序列化 DTO；Unity 官方允许在后台线程调用 [JsonUtility.FromJson](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/JsonUtility.FromJson.html)。场景、UI 和纹理对象不交给后台解析。

初版命令回归通过后，用户仍观察到加载期间手柄、射线和光标停住。进一步检查发现，页面发布时批量创建卡片及同步图片解码仍会产生长帧。`EmbyBrowserUI` 因此增加分帧构建：

- 首页媒体库、继续播放/最新影片卡片，以及七种媒体库视图的可见卡片池，每帧最多创建一张。
- 页面或账户变化时清空待建卡片；逐帧创建的卡片按当前滚动位置绑定，保留有界池和滚动恢复。
- 三路图片下载仍可并发，但每帧最多解码一张图片，并等待卡片构建完成；等待后重新检查代次、可见需求和取消状态。

增加 `Emby.Render`、`Emby.BuildCard`、`Emby.DecodeImage` 性能标记。Development/Editor 诊断记录输入循环次数、最大间隔、有效姿态采样及变化计数，不记录姿态坐标。自动测试在检查实际输入路径前退出模拟指针模式，防止把开发输入响应误当成真实手柄更新。

新增回归覆盖：

- 挂起后台解析时调用方仍可继续执行，解析完成后返回原调用线程，保留中文、BOM 与归一化元数据。
- 解析前取消不启动解析，解析期间取消丢弃结果，无效 JSON 保留安全错误。

- 大列表初次渲染不一次性创建卡片，每次构建仅增加一张；替换页面丢弃旧待建卡片。

原有列表测试改为异步等待。首轮曾因旧同步断言等待 Unity 上下文而挂起，未计入通过结果；修正后从头运行。原始测试及编辑器恢复记录在忽略的 `Docs/Validation/emby-loading-20261017/` 和 `Docs/Validation/EmbyLoadingHitches/`。构建引起的字体、项目设置写入已恢复到构建前字节，场景哈希一致，保留用户原有修改。

### 性能采样边界

使用 [Unity Android 官方命令行性能采样方式](https://docs.unity.com/en-us/engine/6000.3/manual/platform-specific/android/developing/testing-and-debugging/profile-on-an-android-device) 生成本轮二进制性能文件。Editor 保留的最后 2,000 帧：主线程 p50 13.960 ms，p95 15.635 ms，最大 47.804 ms，6 帧超过 25 ms，2 帧超过 40 ms，无超过 70 ms 的帧。对应标记最大值：页面渲染 15.076 ms、单卡构建 4.510 ms、图片解码 0.590 ms。

之前仅做后台解析的版本，在保留窗口内可见 76–99 ms 的页面创建帧；还出现截图/生命周期相关长帧，不能全部归因于媒体库加载。两次窗口都不是完整运行，场景也包含测试命令，因此不据此宣称全程稳定 72 FPS 或严格性能改善比例。原始导出在忽略的 `Docs/Validation/EmbyLoadingHitches/`。
